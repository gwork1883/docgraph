✅ DocGraph 的优势

  • 🔗 1. 结构化关系感知 — 核心差异化优势
    传统 RAG 只能找到"语义相近的文本块"，无法理解文档间的结构性关系。DocGraph 知识图谱提供：
    • 层级关系：Product → Module → Document → Section，AI 可从具体问题向上追溯到所属模块/产品
    • 语义关系：describes（描述术语）、mentions（提及概念）、exposes_api（暴露接口）
    • 影响链分析：doc_impact 做 BFS 多跳遍历，可回答"如果这个 API 变了，哪些下游受影响？" — 这是 RAG 完全无法做到的
  • 🎯 2. 多策略搜索级联 — 比纯向量搜索更精准
    搜索是9 层级联策略而非单一向量匹配，每种策略覆盖不同检索场景：
entity_exact → API路径/代码符号精确匹配 // RAG 对此几乎无能为力
↓ entity_normalized → 归一化匹配（大小写/路径）
↓ FTS5 Unicode61 → BM25 评分全文检索
↓ FTS5 Trigram → 子串/符号模糊匹配
↓ original_unicode61 / trigram → 原始查询回退
↓ exact_terms → 必保留术语 LIKE 搜索
↓ profile_fallback → TF-IDF 检索画像 // 中文 n-gram 1-4字滑动窗口
↓ like_fallback → 最后兜底
↓ vector → 向量相似度搜索 // VectorOnlyPenalty=30 惩罚纯向量命中
  • 🤖 3. MCP 工具范式 — AI 按需探索而非一次性注入
    传统 RAG：一次性把检索结果塞进 prompt → LLM 基于有限上下文回答。
    DocGraph MCP 让 AI 自主决定探索路径：
AI: doc_search("认证流程") // 得到摘要 + section_id
→ doc_get_section(id=...) // 深读具体章节
→ doc_related(id=...) // 发现关联文档/术语
→ doc_impact(id=..., direction=out) // 分析影响范围
→ doc_propose_relation(...) // 主动标注文档间关系

// 这是渐进式探索，而非一次性注入。AI 可根据前一步的结果决定下一步查什么。
  • 🔍 4. 可追溯性与可审计性
    • 每条边都有 Provenance（来源：sync / rule / html_link / manual）
    • 搜索结果有 ScoreBreakdown（精确列出每个 boost 来源和分值）
    • 向量搜索有 Trace（chunk_id、embedding_model、generator_version）
    • 反馈系统可标记 relationship_wrong、document_stale、document_canonical

    RAG 方案几乎不提供这种粒度的可审计性。
  • 🔄 5. 人工反馈闭环 — 自我纠错能力
    • doc_propose_relation：AI 可提议文档间关系（如"这篇文档已过时"），经人工审批后影响检索
    • document_canonical boost：标记权威文档，搜索时优先呈现
    • document_stale 过滤：标记过时文档，搜索时排除

    传统 RAG 没有这种纠错机制 — 错误的检索结果会反复出现。
  • 🔒 6. 内容地址稳定 ID — 幂等同步
    SHA-256 基的稳定 ID 使得重复同步不会产生冗余数据。RAG 方案通常用随机 ID，重新索引会产生重复切片。

❌ DocGraph 的劣势

  • ⚙️ 1. 图谱构建复杂度高
    • 需定义节点/边类型、层级结构、provenance 体系（sync.go 866 行）
    • 对无结构的杂散文档（零散笔记、聊天记录），图谱构建价值有限
    • RAG 方案更简单：切块 → 嵌入 → 存向量库，无需理解文档间结构关系
  • 📦 2. 向量搜索需要 pgvector 外部依赖
    DocGraph 向量搜索需要 PostgreSQL + pgvector，而项目核心理念是"单一 Go 二进制、零外部依赖"。引入 pgvector 打破了这一承诺。
    传统 RAG 方案本就依赖向量数据库，这不是额外负担。
  • ⏱️ 3. 图谱遍历延迟可能更高
    • doc_impact BFS 在 Go 层实现（非递归 CTE），多层遍历需多次数据库查询
    • 大规模图谱（百万级节点）BFS 性能可能成为瓶颈
    • 向量数据库（Milvus/Pinecone）在 ANN 检索上有成熟 HNSW 优化，延迟通常更低
  • 💰 4. MCP 交互需要多轮 LLM 调用 — 成本和延迟
    传统 RAG：单次检索 + 单次 LLM 调用。DocGraph MCP 下，AI 可能需要 3-5 次工具调用：
    search → get_section → related → impact → propose_relation
    每次工具调用 = 一次 LLM 推理，token 消耗和延迟显著增加。
  • 🔧 5. 搜索策略级联可能过度复杂
    9 层搜索策略 + 多种 boost/penalty 组合，覆盖全面但：
    • 调优困难（多个权重参数相互影响）
    • 某些策略对特定领域可能是噪音（如 like_fallback 对英文文档价值有限）
    • RAG 的向量检索虽然"粗糙"，但行为更可预测
  • 📋 6. 知识图谱覆盖范围受限于预定义类型
    节点/边类型是预定义的（Product/Module/Document/Section/API/Term），对不属于这些类型的内容（非技术文档、叙事性内容、多媒体）表达力不足。
    RAG 对任何文本平等对待，无结构限制。

🔑 核心结论

从"语义相似度匹配"升级到"结构化关系推理"

DocGraph 的 MCP + 知识图谱方案的本质跃迁：

1 AI 可以理解文档间的关系，而非仅仅找到"看起来类似"的文本块。图谱遍历让 AI 能够沿层级和语义边进行推理，这是向量检索的语义相似度无法替代的。
2 多策略搜索比纯向量更精准，尤其对代码符号和 API 路径。entity 精确匹配 + FTS5 BM25 + 向量补充的组合，覆盖了向量搜索的盲区。
3 反馈闭环让系统可以自我纠错，这是 RAG 的盲区。标记 document_stale、relationship_wrong、document_canonical 构建了持续改进的闭环。

代价：

A 架构复杂度更高（图谱构建 + pgvector 依赖 + 多轮交互成本）
B 对无结构内容的覆盖不如 RAG
C 规模化场景需要更多优化工作

🎯 最佳策略是 DocGraph 已经在做的事情 — 混合方案：知识图谱负责结构化推理，向量搜索补充语义匹配，两者结合而非互斥。VectorOnlyPenalty 和 strong_hybrid evidence level 设计正是这个思路的体现。
